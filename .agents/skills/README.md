# Codex 決策分析技能使用指南

這裡有八個技能，協助你把業務問題逐步轉成分析證據、候選行動與決策報告。新題目先讓 AI 推薦並釐清研究問題，經你確認後再由 AI 擬定假設與分析計畫；已有專案則依目前需要選技能。提供資料位置與希望回答的問題；不確定從哪裡開始，就用 `$decision-analysis`。

技能由目前的 Codex session 執行，可以反覆切換；不需要一次跑完所有角色。這份指南以 Codex 的 `$技能名稱` 為例；Claude Code 的對應入口及底層命令見 [Harness 操作文件](../../docs/harness.md)。

## 先依情境選技能

| 你目前的情境 | 使用技能 | 可以期待什麼 |
| --- | --- | --- |
| 有需求，但不知道先做什麼；或要接手舊任務 | `$decision-analysis` | 判斷目前需要的角色與下一步 |
| 「想改善良率」太模糊，或想建立嚴謹研究方向 | `$ds-frame` | 定義問題並請你確認，再推導假設、反證與推薦計畫 |
| 缺少震動、忠誠度等想觀察的直接訊號 | `$ds-proxy` | 有理由的替代特徵與驗證方案 |
| 想找差異、關聯、趨勢，或驗證某個猜測 | `$ds-eda` | 圖表、效果量、樣本數、不確定性與限制 |
| 已有發現，想知道何時應提示現場檢查 | `$ds-rules` | 可解釋的候選條件與誤報漏報評估 |
| 想知道某個行動是否值得投入 | `$ds-impact` | 成本來源、效益情境、ROI 與損益兩平條件 |
| 已有證據和報告草稿，想檢查有沒有漏洞 | `$ds-review` | 綁定目前版本的審查結果與修正清單 |
| 想把分析整理成可交接的決策報告 | `$ds-deliver` | 報告草稿、審查協調與通過後的本機交付快照 |

## 第一次使用

### 在哪裡輸入

從 repository 根目錄開啟 Codex，在**對話輸入區**貼上以下提示。`$ds-eda` 這類文字是技能呼叫方式，應放在對話中；終端機只用來執行後文標示為 Bash 的命令。

```text
使用 $decision-analysis。
我想了解哪些條件與良率下降有關，先幫我定義分析問題。
資料位置：<資料 CSV 路徑>
欄位字典：<Schema 或資料字典路徑>
請將本次任務保存在 projects/factory-quality。
先以 EDA 為目標，釐清並向我確認完整研究問題。
確認後再推導假設、替代解釋與推薦分析順序，依計畫執行。
```

將 `<資料 CSV 路徑>` 等欄位換成實際可讀取的本機路徑。各範例共用 `factory-quality` 作為案例名稱；它不是隨專案附上的既有分析。不同決策使用不同 case，同一決策續作時沿用原 case。

只有 Schema 時，也可以先開始：

```text
使用 $ds-frame。
我只有 <Schema 路徑>，還沒有實際資料。
請先釐清要做的決策、資料可取得時間與缺口，提出分析計畫。
本次 case 使用 projects/factory-quality。
這一輪停在問題定義，尚未取得資料的地方保留為待確認。
```

### 你需要準備什麼

至少說明「想決定什麼」與「現有資料在哪裡」。有目標指標、比較基準、時間範圍、欄位單位或現場限制時，一起提供；缺少的條件可以先盤點。

Case 是這次決策的獨立專案目錄。init 會建立 research/、data/、analysis/、config/、reports/、artifacts/、state.sqlite 與交接骨架，分開保存本題的素材、程式、參數與報告。完整配置見 [研究流程與專案目錄](../../docs/research-workflow.md)。Agent 依技能執行初始化、角色登錄與證據保存；你不必在每輪對話手動操作所有命令。Harness 本身只需要 Python 標準函式庫；使用 Python 分析套件時，依專案環境執行 `uv sync --locked`。

## 每個技能怎麼用

### decision-analysis 選擇角色與接手任務

**適用情境：**需求還不清楚、不知道選哪個技能，或換了一個 session，要接續既有分析。

**先準備：**業務需求；若已做過分析，提供 case 路徑與這次想繼續處理的問題。

```text
使用 $decision-analysis 接手 projects/factory-quality。
先檢查目前狀態與有效證據，告訴我已完成什麼、哪些已過期。
我現在想知道夜班差異是否只是產品組合造成的。
請從必要的環節續做，保留既有可用結果。
```

**預期產出：**目前狀態摘要、需要補足的資訊與適合的下一個角色。路由本身沒有固定的分析報告檔名；實際證據由被選中的角色產生。

**下一步：**第一次分析通常先進入 `ds-frame`；已有 case 則依狀態與問題選擇角色。它不會強制跑完整條分析管線。

技能定義：[decision-analysis/SKILL.md](decision-analysis/SKILL.md)。

### ds-frame 確認研究問題並推導分析計畫

**適用情境：**只有「降低流失」「提升良率」等目標，尚未說清楚誰在什麼時間需要做什麼決定；或分析途中發現原問題需要重定義。

**先準備：**業務背景、可採行動、資料字典，以及已知的目標或限制。

```text
使用 $ds-frame，case 為 projects/factory-quality。
我們想找出值得安排人工檢查的生產批次，現有欄位見 <Schema 路徑>。
請定義觀測單位、檢查決策時點、結果指標與比較基準，
區分「良率下降 5%」與「下降 5 個百分點」。
先推薦完整研究問題及資料缺口，請我確認。
我確認後，再比較來源與替代解釋，推導假設、反證條件與分析順序。
不預設一定要建模型，也不把方法設計拆成選單讓我逐項挑。
```

**預期產出：**`research/question.md` 登錄為 frame；取得你對目前版本的明確確認後，保存確認來源，再產出 `research/plan.md` 登錄為 plan，並維護 hypotheses.md 與 sources.md；每輪假設結果另外寫入 findings.md。計畫包含假設依據、替代解釋、反證、方法、順序與停止條件。

**你要判讀：**問題是否符合實際決策，指標是否量得到，行動時點是否正確。AI 提出的工作假設應與已確認條件分開。

**下一步：**問題確認與有效 plan 完成後，缺少直接訊號時進入 `ds-proxy`；已有可用欄位時進入 `ds-eda`。只有 Schema 的任務可先停在定義或假設提案；這不代表已完成 EDA 或正式交付。

技能定義：[ds-frame/SKILL.md](ds-frame/SKILL.md)。

### ds-proxy 提出代理特徵與量測替代方案

**適用情境：**你知道想觀察的概念，但資料沒有直接量測；例如沒有震動感測值，只有電流、耗電與維修紀錄。

**先準備：**已確認的問題定義、有效 plan、Schema、欄位單位、取樣頻率、資料延遲與可用的驗證紀錄。

```text
使用 $ds-proxy，接續 projects/factory-quality。
我們沒有震動資料，只有每分鐘平均電流、耗電與維修紀錄。
請比較合理的設備異常代理特徵，逐項說明：
計算定義、單位、領域理由、決策當下能否取得、混雜因素與驗證方式。
分鐘資料無法驗證的高頻現象請列為限制，並記錄不採用的候選。
```

**預期產出：**`proxy.md`，包含候選特徵、替代方案、理由、限制與驗證方式。候選會依證據標記為：

| 標記 | 意義 |
| --- | --- |
| `hypothesis` | 尚待驗證的假設 |
| `domain_confirmed` | 有使用者或具名來源支持的領域確認 |
| `empirically_validated` | 有實際驗證證據支持；適用範圍仍需說明 |

**你要判讀：**代理訊號是否有合理機制、是否當下可用，以及它真正代表什麼。領域確認不等同實證驗證，AI 也不能代替你核准物理假設。

**下一步：**交給 `ds-eda` 量化檢查；現有資料無法支持時，交付追加量測方案。

技能定義：[ds-proxy/SKILL.md](ds-proxy/SKILL.md)。

### ds-eda 探索資料與檢查假設

**適用情境：**想找群組差異、趨勢、關聯與資料品質問題，或針對特定切角追問。

**先準備：**已確認的 `frame`、有效 `plan`、資料位置與字典；已有代理特徵時一起提供。若需要獨立驗證，先明確保留資料範圍。

```text
使用 $ds-eda，接續 projects/factory-quality。
資料位於 <資料 CSV 路徑>。請先檢查缺值、觀測單位與時間結構，
再比較相同產品與相近負載下，日班和夜班的良率差異。
回報效果量、各組樣本數、不確定性與多重比較處理，
附上能回答問題的圖表，保留不成立的假設與重現方式。
本輪只使用開發資料，依研究計畫說明推薦順序並主動檢查反證。
```

**預期產出：**以 inquiry 模板撰寫的每輪 `eda.md`、圖表、統計結果與可重現程式或查詢。報告說明方法選擇、假設檢查、主要發現、不成立的假設及限制。

**你要判讀：**差異是否具有業務意義，是否可能來自產品、設備或其他混雜因素。P-value 小不代表效果重要；不顯著也不能直接解讀為沒有影響。

**繼續探勘時可直接追問：**

```text
接續同一個 case。請按設備拆開比較，保留原本整體結果供對照。
若方向反轉，先檢查群組組成；新增切角維持探索狀態。
```

**下一步：**證據已足以支持判讀時可交給 `ds-deliver`；需要操作條件時用 `ds-rules`，需要成本比較時用 `ds-impact`。

技能定義：[ds-eda/SKILL.md](ds-eda/SKILL.md)。

### ds-rules 將發現轉成候選警報條件

**適用情境：**已有分析證據，現場需要知道哪些條件觸發時應安排人工檢查，或希望形成 SOP 草案。

**先準備：**有效的 `frame` 與 `eda`、可用特徵、事件定義、可採行動，以及能接受的誤報漏報負擔。

```text
使用 $ds-rules，接續 projects/factory-quality。
依現有有效證據探索可解釋的人工檢查條件。
門檻只在開發資料調整，規則凍結後再用保留的後期資料評估。
請列出條件與單位、涵蓋率、事件比例、誤報漏報與不確定性，
並說明觸發後的處置、適用設備模式與試行退出條件。
樣本不足的規則保留為候選。
```

**預期產出：**`rules.md`、候選條件與評估結果，包含未通過或不穩定的規則，以及試行和退出條件。

**你要判讀：**規則能否在決策時算出來、現場能否回應，以及警報成本是否可接受。樹的分割條件仍須經獨立驗證；依驗證結果改過門檻後，需重新安排獨立評估。

**下一步：**需要比較投入時交給 `ds-impact`；準備整理候選方案時交給 `ds-deliver`。這個技能產生候選與建議，不會直接部署警報。

技能定義：[ds-rules/SKILL.md](ds-rules/SKILL.md)。

### ds-impact 計算成本與效益情境

**適用情境：**想評估是否值得試行，或比較不同投入和改善假設下的商業價值。可以直接根據 EDA 估算，不要求先有規則或模型。

**先準備：**有效的 `frame` 與 `eda`、擬採取的行動、成本期間、成本來源與介入效果的證據或假設；已有規則時一併提供。

```text
使用 $ds-impact，接續 projects/factory-quality。
我們想評估提前檢查是否值得試行，成本參數見 <成本參數檔路徑>。
請分列觀測值、使用者提供值與情境假設，統一期間與幣別，
計算保守、基準、樂觀情境，以及最敏感假設的損益兩平點。
改善幅度若缺乏介入證據，保留為假設；缺少成本的地方明列缺口。
```

**預期產出：**`impact.md` 與可重算的試算檔或程式，包含參數來源、公式、情境、敏感度、損益兩平與試行指標。

**你要判讀：**成本是否漏列或重複計算、改善假設是否合理。ROI 使用同期間的淨效益除以總投入；總投入為零時不計算 ROI。缺乏真實成本仍可做明標假設的示意，估算節省須與實測效益分開。

**下一步：**交給 `ds-deliver` 整理試行決策與後續量測方案。

技能定義：[ds-impact/SKILL.md](ds-impact/SKILL.md)。

### ds-review 審查證據與報告

**適用情境：**已有分析證據和交付草稿，準備讓其他人依報告做決定，或擔心洩漏、推論和成本假設有漏洞。

**先準備：**case 路徑、報告草稿、有效分析證據，以及實際資料、程式和計算輸出的路徑。尚無草稿時，可先用 `ds-deliver` 整理。

```text
使用 $ds-review，審查 projects/factory-quality。
交付草稿位於 <決策報告草稿路徑>。
請先建立審查起點，核對決策範圍、資料洩漏、統計方法與業務假設，
每項問題附證據、嚴重程度與處理狀態。
審查中先記錄問題，修正另開一輪；並如實標明本次審查來源。
```

**預期產出：**`review.json` 與工具登錄的版本綁定審查紀錄。審查結果為 `pass`、`revise` 或 `blocked`；重要問題未解決時，不能以 `pass` 登錄。

**你要判讀：**每個結論是否對應實際證據，以及審查範圍是否涵蓋報告主張。同一 agent 自我審查應標明；切換角色名稱不能當作獨立審查。

**下一步：**`pass` 後以同一版本報告交付；`revise` 回到相關技能修正，再重新審查。`blocked` 應說明需要補足的條件。審查後修改報告文字或證據，也需要重新核對與審查。

技能定義：[ds-review/SKILL.md](ds-review/SKILL.md)。

### ds-deliver 整理報告與完成本機交付

**適用情境：**分析已有可用成果，希望整理成決策者讀得懂、後續協作者能接續的報告。

**先準備：**case 路徑、本次交付目標與讀者。已有草稿或審查結果時提供其路徑。

```text
使用 $ds-deliver，整理 projects/factory-quality。
讀者是產線主管，請先回答是否值得安排小規模試行，
再列關鍵證據、適用限制、候選行動、成本假設與下一步。
只使用有效證據；整理草稿後協調 ds-review，通過後交付相同版本。
最後回報報告路徑、審查來源、review_id 與可接續事項。
```

**預期產出：**依成果選 exploration-summary 或 decision-report 模板撰寫報告草稿；審查通過後，工具建立本機交付快照，回傳路徑與 `review_id`，並可查到 `delivery_current`。只有 EDA 的任務可交付分析發現，不需要補做 ROI。

**你要判讀：**報告是否回答原問題，是否說清楚行動條件、證據強度與尚未成立的假設。

**下一步：**以交付版本支持討論或規劃試行。GitHub 推送、警報部署與現場執行，依另外的任務授權處理。

技能定義：[ds-deliver/SKILL.md](ds-deliver/SKILL.md)。

## 常見任務怎麼組合

| 任務 | 建議路徑 | 可以停在哪裡 |
| --- | --- | --- |
| 只有 Schema，先評估能研究什麼 | `frame → 人類確認 → plan → proxy（按需）` | 問題定義、假設與補資料清單 |
| 想了解客戶流失的關聯因素 | `frame → 人類確認 → plan → eda → deliver`，deliver 協調 review | 經審查的關聯報告與下一步 |
| 想形成設備人工檢查條件 | `frame → 人類確認 → plan → proxy（按需）→ eda → rules → deliver` | 候選警報、驗證結果與試行草案 |
| 想比較行動是否值得投入 | `frame → 人類確認 → plan → eda → impact → deliver`，rules 按需 | 成本效益情境與試行評估方案 |
| 接手舊任務、資料或結論有修改 | `decision-analysis → 狀態檢查 → 受影響角色` | 修復過期部分，再審查交付 |

每條正式交付路徑都是「草稿 → review → 通過後交付」。缺少實際資料時可以先產生定義或假設文件，不能把它描述為已完成統計分析。

## 如何做多輪探勘

在同一個 case 中，直接針對現有結果追問：

```text
接續 projects/factory-quality，使用 $ds-eda。
請比較加入產品分層前後的結果，並主動找一個可能推翻原解釋的切角。
保留本輪分析程式、圖表與未成立的發現，說明哪些是新增探索。
```

Agent 可以在 case 的工作子目錄保留每輪文件；目前 runtime 以各 stage 的當前版本管理正式證據。更新上游或重新登錄 EDA 後，相關下游和 review 可能過期，下一輪先查狀態。逐題探索看板與獨立分支管理仍非目前內建功能。

每輪由 agent 回報回答的假設、證據、反證與限制，再說明推薦下一步的理由。已確認問題與授權範圍內，AI 可持續執行計畫；遇到核心問題改變時才重新向你確認。

## 產出在哪裡與如何接手

研究問題與計畫固定放 research/question.md、research/plan.md；分析程式放 analysis/、資料放 data/、結果放 reports/，每輪使用 reports/explorations/<輪次>/。`eda.md` 等文件的具體輪次路徑由 agent 回報。經 `record` 登錄後，工具會在 case 的 `artifacts/` 另外保存具有識別碼的快照；不要只靠猜測檔名找結果。

```text
projects/factory-quality/
├── state.sqlite       任務狀態、相依版本與 review 紀錄
├── artifacts/         已登錄的證據、審查與交付快照
├── research/          問題、確認、計畫、假設與來源
├── data/              raw、interim、processed
├── analysis/          本題程式與 notebook
├── config/            本題參數
├── reports/           每輪結果、圖表與決策報告
└── handoff.md         接手資訊
```

換 session 或換 host 時，提供同一個 case 路徑並要求先檢查狀態。也可自行在 repository 根目錄執行：

```bash
python3 tools/ds_harness.py status --case projects/factory-quality
```

| 狀態欄位 | 解讀方式 |
| --- | --- |
| stage 為 `current` | 已登錄文件、輸入與上游版本符合一致性檢查；內容品質仍需審查 |
| stage 為 `missing` | 尚未登錄；可選環節不必全部完成 |
| stage 為 `stale` | 輸入、文件或上游已有變動，需要核對並重做受影響部分 |
| `problem_confirmed` | 目前 frame 版本是否有有效的使用者確認來源 |
| `next_action` | 需定義問題、等待確認、寫計畫、分析或整理交付 |
| `review_current` | 目前候選是否具有有效的通過審查 |
| `delivery_current` | 最近交付是否仍對應目前有效審查及快照 |
| `next_skill` | 工具依必要上游與失效情形提示的下一個角色；分析切角仍由 agent 與你判斷 |

Case 的 `goal` 可為 `eda`、`rules` 或 `impact`，代表本次正式交付所需達到的分析目標。`frame`、`plan`、`proxy`、`review`、`deliver` 是角色或環節，不是 `init --goal` 的選項。

## 常見問題

**一定要先手動建立 case 嗎？**

不必。告訴 agent 新 case 的路徑與目標，它可以依技能契約初始化；已有 case 時先查狀態，避免重新建立。

**有資料就能直接用 ds-eda 嗎？**

可以直接提出 EDA 需求；若缺少問題定義，agent 先推薦完整問題並請你確認，再由 ds-frame 擬定 plan。這兩項完成後才執行目標導向分析，不能以自動代填跳過確認。

**結果不顯著或找不到可用規則，算失敗嗎？**

只要方法合適、證據與限制清楚，這也是有效成果。可以交付「目前不支持哪項假設、還缺什麼資料、是否值得繼續」的結論。

**Codex 沒有發現技能時怎麼辦？**

先確認從本 repository 開啟 session；必要時重新啟動。仍未發現時，可以請 agent 讀取對應 `skills/<名稱>/SKILL.md.tmpl` 與 `skills/_shared/session.md`，依文件續做，並說明這是手動讀取的替代方式。

**Claude Code 也能使用嗎？**

可以。使用 `.claude/skills/` 的入口，將範例中的 `$ds-eda` 改為 `/ds-eda`，其他名稱同理；兩者共用相同 case 與證據契約。

**想修改技能，要改這裡的 SKILL.md 嗎？**

維護來源是根目錄的 `skills/<角色>/SKILL.md.tmpl`；修改後執行 `python3 tools/render_skills.py --write` 產生兩個 host 的入口。這份 README 是使用指南，不由 renderer 產生。

## 方法參考與報告骨架

技能會依工作內容選讀共用及角色 references：新資料先理解品質，需要選方法時核對比較設計；重複量測讀相依資料，群組差異檢查混雜。每輪探勘使用 inquiry，收斂時選探索摘要或決策報告骨架。這是 agent 的按需讀取規則，詳細入口見 [技能參考與模板](../../docs/skill-resources.md)。
