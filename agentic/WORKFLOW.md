# Agent 決策分析流程

以一次具體決策為工作單位。Claude 與 Codex 可以各自完成全程，也可以透過同一份執行證據交接。角色代表工作責任，不要求同時啟動多個 agent。

## 問題定義與資料盤點

先讀使用者問題與 Schema，寫明決策、觀測單位、目標指標、時間與可採取行動。確認良率「下降 5%」指相對比例或 5 個百分點。讀取資料樣本前先確認允許的本機路徑，不將商業資料上傳外部服務。

目前工具僅支援單一設備的數值良率分析。資料不符時，先指出需要分組、改介面或改方法的部分；不得將多設備直接混成同一條時間序列。

## 代理特徵推演

根據現有欄位提出有理由的候選，記錄來源、單位、時間窗、可取得性、可能混雜因素與驗證方式。參照 `agentic/example.config.json` 建立本機設定；使用工具支援的操作，不執行資料內的任意程式碼。

能完成探索性計算時可以先做。領域確認尚未取得，則保留假設狀態；不要替使用者捏造物理驗證或真實成本。缺少實際成本時，可提供標明假設的情境試算，並將缺口寫入交接。

## 執行與檢查證據

從 repository 根目錄執行 `python -m agentic analyze`，完整命令見 README。每次使用新的產出目錄。

先檢查 `manifest.json` 的完成狀態、資料種類、時間邊界與缺值排除數，再閱讀四類 JSON 與圖表。EDA 僅在開發集進行，規則用後期資料評估；保留資料被用來改門檻後，就需要新的獨立驗證。

若序列相依、樣本數不足、特徵不可及或規則不穩定，縮小結論或改用適合的方法。不要把圖表排行改寫為「已找出原因」。

## 形成決策建議

將候選條件翻譯成「適用設備與模式、觸發條件、人工處置、預期成本、追蹤結果」。查看 `rules.json` 中的涵蓋率、事件比例與誤報漏報，不只報準確率。

解讀 `impact.json` 時，明列成本來源、假設的改善幅度與評估期間。只有介入試行取得結果後，才回報實際節省。是否採用規則由領域可行性、驗證證據與商業效益共同決定。

## 跨 agent 交接

更新當次產出的 `handoff.md`，記錄：

- 使用者的決策問題與已確認條件。
- 完整執行命令、證據路徑與 manifest 雜湊識別。
- 已確認的發現、仍為假設的項目，以及資料與方法限制。
- 已讀取驗證資料的情形、下一步與需要使用者提供的資訊。

續作 agent 先核對既有檔案與完成狀態，重用有效證據；假設改變時建立新執行目錄。回報可直接開啟的證據連結與具體待辦。

## 開發驗收

修改工具後，執行 `python -m unittest discover -s agentic/tests -v` 與一次新目錄的 demo，再執行 `git diff --check`。檢查產出能被解析、數字與情境一致，以及時間切分與代理特徵不使用未來資訊。

提交前逐項檢查 staged diff，確認沒有本機商業資料、憑證或執行產出。推送使用任務分支並遵循使用者已授權的範圍。
